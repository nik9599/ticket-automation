# SKILL: in-depth research (any repo, any step)

Why this exists: step 2 once classified tickets wrongly because it grepped once for the ticket's exact words, found nothing, and stopped.
The features already existed under other names (a "Languages" card and a per-item "Translate" popup; a per-item visibility rule that one surface
simply never called), so the right verdicts were "already supported" and "small reuse", not "backend only" or "needs info".
Lesson: one grep for the ticket's exact words is NOT research. Look for the feature under every name it could have, then trace the data end to end.

## When to run it (MANDATORY)
Step 2 MUST run this skill before it sets any of these verdicts: `be`, `needs-info`, or a feature request / "not supported" / "no existing pattern".
Also run it whenever the ticket asks a question ("is it possible", "can we", "is there a way", "how to configure", numbered questions), and in step 3
when the handover leaves the cause or the place unclear. Read-only: never edit repo code, never click Save anywhere, test store / local only.
Time budget: about 10 minutes; stop earlier when every question below has an answer with a file:line.

## 1. Split the ticket into questions
Write every question and every requirement as its own line (Q1, Q2 ...), including the implied ones ("is it supported today?", "how do I set it up?",
"can it be done in the front end?"). Each one must get an answer in step 6. Never answer only the last question.

## 2. Synonyms before grep
List 5-10 names the feature may have in the code and in the UI, e.g.
translation -> translat, language, locale, languageCode, i18n, labelTranslation, Languages;
visibility -> visible, hide, hidden, show, memberOnly, inclusiveTags, exclusiveTags, customer_tags, excluded;
Search ALL of them. Always on `origin/<base>` (`git fetch -q origin <base>` first, base = $TICKET_BASE_BRANCH, then `git grep -n -i '<term>' origin/<base> -- <paths>`), not the working tree.

## 3. Search every layer of THIS repo (where things live)
Use the "Research map" table in `<project_dir>/project.md` (generated by step 0) plus `<project_dir>/<surface>.md`. Typical layers: settings / admin
UI, customer-facing UI on each surface, labels / translations, API + services, data model + migrations, server templates or scripts that feed the
front end, extensions / widgets, docs. For each layer write "found: <file:line>" or "nothing for <terms>". No research map yet: list the layers
from the folder tree and say "no research map" in the note.

## 4. Trace the data end to end
For the feature (or the closest existing one) follow it through every hop and write the chain with file:line:
admin UI field -> save API / DTO -> stored column -> how the customer-facing side gets it (API response, config injected into a page, template,
GraphQL) -> where it is rendered or checked -> which other surfaces read the same data (twins in the surface maps).
Also check who does NOT read it (a surface that never calls the shared check is often the whole answer).
Request parameters matter: note which call passes language / customer / region and which does not.

## 5. Feasibility verdict
Pick ONE and prove it:
- **already supported**: it exists today; write the exact user steps (menu path > field > value). Verdict `config` if that solves the ticket.
- **front-end only**: the data is already in the front end; list files and the smallest change. Verdict `code`.
- **mixed**: small BE part + FE part; list both (BE = field/endpoint/DTO, FE = files). Verdict `code` for FE + ONE "For BE team:" comment, per replicate_classify.md.
- **backend only**: prove why the front end cannot do it (which data/decision only the backend has). Verdict `be`.
- **needs product decision**: only when the spec is truly missing (wording, which plans, what happens in edge cases); name exactly what is missing.
Reusing an existing pattern counts as feasible: say which pattern and where.
Always list edge cases and limits (e.g. "hidden in our UI only; the platform still accepts it through another entry point").

## 6. Write it down
Create `{{AUTOMATION_DIR}}/evidence/<id>/research.md`:
```
# Research <id>
Questions: Q1 ... -> answer (file:line) ; Q2 ... -> answer
Search terms: ...
Layers searched: <layer>: found <file:line> | nothing for <terms>
Data flow: A (file:line) -> B -> C ; not read by: ...
Verdict: already supported | front-end only | mixed | backend only | needs product decision
What we need: table Part | Change | Size (BE / FE per surface)
Open decisions: ... (or none)
```
Then `ledger.py set <id> --evidence evidence/<id>/research.md --note "RESEARCH: <verdict> - <one line>"`.
Copy the answers into the handover (verdict code) or into the ClickUp comment (config / be / mixed): the comment must answer EVERY question from step 1,
the supported parts first, then "For BE team:" only for what is really missing.

## 7. Self-check before you finish (all must be yes)
- Every question from step 1 has an answer with a file:line or a menu path.
- At least 5 search terms, all layers of the repo map checked.
- Existing settings/translations/visibility features looked for under synonyms.
- The data flow is written end to end, including who does not read the data.
- A `be` / `needs-info` verdict says exactly why the front end cannot do it / exactly what is missing.
If a check is "no", keep researching or say so in the note ("RESEARCH GAP: ...").
After the ticket: `python3 {{AUTOMATION_DIR}}/tools/lessons.py add --surface <s> --ticket <id> --text "<where the feature lived>"` when you found something non-obvious.
