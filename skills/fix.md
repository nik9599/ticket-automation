# STEP 3: fix the code (one ticket, Opus). Work in the repo's MAIN checkout, on the ticket's own local branch from origin/<base_branch> (no worktrees).

> LIVE RULE (whole step): anything that changes data happens only on the ticket repo's test environment. Live environments: view only
> (skills/live-view-only.md), logged in evidence/<id>/live-log.md. See guardrails.md.

Input: TICKET_ID, TICKET_REPO, TICKET_BASE_BRANCH. Stage flow: classified -> fixing -> fixed-local (or needs-human). Verdict must be `code`.
FRONT-END ONLY: never edit profile `backend_paths` or `never_change`; if the fix needs it, stop, put that part in the note, needs-human.
No push, no PR, no merge, no tracker comment.

1. Start
   - `ledger.py show <id>`; `ledger.py set <id> --stage fixing`. FIRST read `{{AUTOMATION_DIR}}/evidence/<id>/handover.md` (surface, root cause, files,
     proposed change, copies, repro, nearby tests, test idea, open decisions) and go straight to those files. Missing file (old ticket): use the
     ledger fields. Deviating from "Files to change" / "Proposed change": say why in the note. Open decisions go into the note for {{OWNER_NAME}}.
   - Lessons: `python3 {{AUTOMATION_DIR}}/tools/lessons.py show --surface <surface>` and `--surface general`.
   - PROJECT FILES (generated by step 0): `<project_dir>/project.md` (folder lock, copies, tests, run notes) ALWAYS, and the surface map
     `<project_dir>/<surface>.md` (where code lives, feature -> twin table, deprecated folders, traps, tests). Read these INSTEAD of browsing all docs.
     Check every twin the map lists for the changed feature: fix it too, or say why not. Never change deprecated / never_change folders.
     No map for the surface: use the profile's context_docs and say "no surface map" in the note.
     A wrong path in a map or a new trap that cost time: add a lesson (step 6) and say "project file update: <what>" in the note.
   - Commands come from the profile (`python3 {{AUTOMATION_DIR}}/config.py profile $TICKET_REPO commands`). Never invent a command the profile does
     not list; missing -> write "not run (no command in profile)".
   - Branch (main checkout, repo config -> path):
     1. `git status --short`: only local-only files (profile `local_only_files`) may be modified. Anything else -> needs-human "repo has uncommitted
        changes that are not local-only: <files>" and stop (never stash/reset/discard them).
     2. `git fetch origin <base>` (if it fails, use the existing origin/<base> and say so).
     3. Branch = `python3 {{AUTOMATION_DIR}}/ledger.py branchname --id <id> --title "<title>"`. Exists (a retry from verify) -> `git checkout <branch>`;
        else `git checkout -b <branch> origin/<base>`. Local-only files carry over uncommitted; if git refuses the switch, needs-human.
     4. `ledger.py set <id> --branch <branch>`. Use the repo's installed dependencies (never a full install unless the profile's install command is
        needed and nothing is installed; say so). One ticket at a time.
   - LOCAL-ONLY MODE (owner says "keep code local, no commit"): same branch, leave changes uncommitted, skip the commit; say so.
2. Confirm the cause before editing: follow the repro recipe on the test environment when possible. Not reproducible live: say so and proceed from
   the code only when the cause is certain from reading it.
3. Write the fix:
   - Smallest change that fixes the root cause. No unrelated refactors, renames, formatting sweeps.
   - Follow the surrounding style and the conventions project.md names. Reuse existing helpers.
   - Clear names, short functions, early returns, no clever one-liners, no dead or commented-out code, no stray debug logs, no TODO without a ticket id.
   - Check the other copies of the same rule (twins in the surface map, other surfaces) and fix or deliberately skip them, saying which.
   - NEW CODE: one job per function, descriptive names for values and conditions (`const canPlaceOrderNow = ...`), no nested ternaries, obvious data
     flow, error paths show a clear message instead of swallowing it. Prefer reusing the existing component/helper over a copy.
   - REMEMBERED STATE: if a change keeps or restores something the user set (filters, search, sort, page, tab, selection), the user must SEE it when
     they come back (a "Showing: ..." line or chips, a selected tab) and get a one-click way back to the default ("Clear filters"). Never restore silently.
   - REUSING A FEATURE IN A NEW PLACE: apply exactly the SAME conditions as the original place (eligibility/visibility checks, settings, confirmation,
     success/error handling, labels/translations). Read the original first, list the conditions in the note, reuse its component/helper, and add
     a test proving each condition also holds in the new place.
   - Never touch local-only files; never edit an applied migration.
4. Tests (part of the fix):
   a. NEW tests for the behaviour you fixed:
      - e2e for UI/behaviour bugs, next to the repo's existing e2e specs with the same naming. Test environment or localhost only; read URLs and
        credentials from environment variables (never hard-code a link, token, JWT or password); use `{{AUTOMATION_DIR}}/tools/guard.js` style
        safety for non-test hosts.
      - Unit tests for logic you changed, next to similar existing tests (the profile's test runner).
      - Name tests after the behaviour. Keep each small.
      - UI fixes: the new test must check what RENDERS (render the real component, query the DOM, assert the visible result). Checking only props or
        calls is not enough: a props-only test can pass while the page renders the wrong component.
      - When feasible show the new test FAILS without the fix and PASSES with it (`git stash push -- <your changed source files only>`, run,
        `git stash pop` at once; never stash local-only files). If not feasible, say so.
   b. Existing tests that cover the touched code: profile `commands.test_related` with the changed files. Related e2e specs: run ONLY those that target
      the test environment or localhost; list others as "not run (targets a live environment)". Profile `commands.test_gate`: ALL must pass.
   c. NEVER edit, delete, rename, skip or loosen an EXISTING test (profile `existing_tests_regex`). Fix the source, not the test. After 2 failed
      rounds: needs-human with the failing test names.
5. Check and commit
   - Lint / typecheck / format the changed files only (profile commands). `{{AUTOMATION_DIR}}/tools/check_staged.sh` must print ok.
   - Read every edited file and `git diff` once more before staging.
   - Stage by explicit path. One commit on the ticket branch: title `<short issue> - <ticket link>`, blank line, "Files:" with every changed file
     (incl. new tests), then the Co-Authored-By trailer(s). No push.
6. Notebook (every ticket, success or not): 1-3 short lessons that save time next time:
   `python3 {{AUTOMATION_DIR}}/tools/lessons.py add --surface <surface key or general> --ticket <id> --text "<one plain-English lesson>"`
   (saved in `<project_dir>/lessons.md`; a lesson true for every project: add `--repo general`).
   Good lessons: where a feature really lives, which copies change together, a slow or flaky test, a trap, a command that worked. No secrets.
   An existing lesson that was wrong: say so in the note.
6b. Tested-commit record: after the commit, if you made NO source edit after your last green test_gate run, add to the note
   `TESTED: <git rev-parse HEAD> | gate <suites/tests passed> | typecheck <result> | related <result>` (step 4 then skips re-running them).
7. Hand over: `ledger.py set <id> --stage fixed-local --file <each changed file> --note "<what changed, why, new tests, existing tests run + result,
   tests NOT run and why, gate counts, copies checked>"`. Leave the repo on the ticket branch with a clean tree (only local-only files modified).

## Keep old and new features working
- Bug tickets: read `evidence/<id>/root-cause.md` with the handover. Fix at its "Fix boundary". Never simply revert the commit/PR named in "Why now":
  it serves a newer feature that must keep working.
- Every "Must keep working" row must still hold. Add the tests listed in "Tests step 3 must add" (bug case + each old/new feature row the change can
  affect) and show they pass. Note "MATRIX: <row> ok (test <name>)" per row. A row that cannot hold: needs-human, say which.

## Simple, readable code, minimum comments
- Simple over clever: plain if/else and early returns; no nested ternaries, no long chained one-liners, no new abstraction for one use.
- Names explain the code (`isExpiredTrial`, `hasVisibleItems`, not `flag`, `tmp`, `data2`).
- Small functions, same patterns as the code around it; reuse helpers.
- Comments: default NONE. One short line only when the WHY cannot be shown by names (a platform quirk, a non-obvious business rule). Never WHAT the
  code does, never ticket ids, dates, "fixed by", commented-out code or TODOs. If the diff needs a paragraph to explain, simplify it.
- Note line: "READABILITY: comments <n> added (why each), new functions <n>".

## Never come back
A fix is done only when the same issue cannot come back unless someone changes this code again:
- Fix the cause at the fix boundary for EVERY breaking variant in root-cause.md, in EVERY copy/twin (incl. generated files, rebuilt with the
  profile's `generated_files` command).
- Forbidden as a fix: delays/timeouts, retry loops, CSS that only hides, swallowed errors, special cases for one customer/record id, one-account data
  fixes. Nothing else works: needs-human with the reason.
- A permanent regression ("lock") test for the bug case and each variant: FAILS on the old code (stash proof), PASSES with the fix.
  Note "LOCK TEST: <file> - <cases>" and "NEVER-AGAIN: variants <n>/<n> covered, copies <list> fixed".

## Speed rules (order and scope only, never the guardrails)
Target about 10 minutes. Never relaxed: no edits to existing tests, the gate must pass, check_staged must print ok.
- Start from the handover; read the named files, direct callers and one sibling for style. The project files replace broad doc reading.
- Order: (1) the new spec(s) alone with the fix; (2) the stash proof ONCE for the new specs; (3) related tests (limit workers to keep the machine
  responsive); (4) the gate ONCE after your last source edit (edited again -> re-run what that edit affects, then the gate a final time).
- Read `<project_dir>/test-baseline.md` (if it exists) first: a failure listed there that fails the same way is pre-existing; list it, do
  not re-prove it. Not listed: run that file alone; still failing -> prove once with a stash. A NEW pre-existing failure: add one line
  "- <file>: <what fails> (<date>)" to `<project_dir>/test-baseline.md` (create it with the title "# Test baseline (known problems on origin)").
- A suite that times out under load: re-run only that file once, serially.
- Tools the profile or a lesson marks as broken here: write "not run".
- Lint / format / typecheck on changed files only.

## How the developer tests
Each ticket's fix is one commit on its own local branch. After the run {{OWNER_NAME}} switches to each branch and tests it. An edit made while
testing is committed on the same ticket branch before the PR.

## Not reproducible on the test environment
Still fix it when the cause is certain from the description and the code (e.g. the difference between two surfaces that should behave the same).
Keep it small, add unit tests for the logic, and note "NOT REPRODUCED ON TEST ENVIRONMENT - needs live check" so steps 4 and 5 handle it.
